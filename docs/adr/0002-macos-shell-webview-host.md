# Separate the macOS shell, React interface, and local Host

Mischief for macOS will use a small Swift/AppKit shell for macOS lifecycle and native actions, a WKWebView for React, and a Node Host for working state. This keeps platform glue out of the domain and leaves room for both the macOS app and VS Code extension to use the same platform-independent controls and domain classes. Extract code into a root-level `shared/` library when Phase 2 provides a second real caller; keep VS Code APIs in `vscode-extension/` and AppKit/WebKit APIs in `macos/`. The alternative of moving product behavior or the extension UI during the packaging prototype would hide whether this three-part shape actually works.

Phase 1 tests the shape with a bundled Node runtime, bundled diagnostic React page, Apple Development-signed arm64 app, Swift-to-child standard input/output, and typed Swift-to-React messages. The app keeps the diagnostic Host running across window close/reopen and stops it on Quit; there is no network listener or profile/Thread access. This is a prototype lifecycle contract, **not** a change to Thread ownership: the VS Code extension remains the sole writer for its live Threads under [ADR 0001](0001-profile-database.md). Phase 3 must explicitly supersede that ownership decision before either client can control the same live Thread. If signing, bundling, or supervision fails in the packaged app, reconsider Electron before moving product behavior.
