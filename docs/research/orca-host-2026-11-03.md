# Orca host architecture (source review)

Reviewed [`stablyai/orca` at `7146038`](https://github.com/stablyai/orca/tree/7146038cd38b8a50766dd2d78e3a8fff4fd097ea) on 2026-11-03. This is a comparison, not a proposed Mischief implementation.

## What runs where

- Orca has **two distinct background roles**, not a single universal daemon. Its **desktop Electron main process** constructs `OrcaRuntimeService` for the local host ([desktop runtime](https://github.com/stablyai/orca/blob/7146038cd38b8a50766dd2d78e3a8fff4fd097ea/src/main/startup/main-process-runtime-service.ts#L70-L97)). A headless **`orcad` Node process** constructs the same runtime and exposes it through `OrcaRuntimeRpcServer` to paired clients ([orcad startup](https://github.com/stablyai/orca/blob/7146038cd38b8a50766dd2d78e3a8fff4fd097ea/src/main/orcad/orcad-entry.ts#L192-L214), [RPC setup](https://github.com/stablyai/orca/blob/7146038cd38b8a50766dd2d78e3a8fff4fd097ea/src/main/orcad/orcad-entry.ts#L298-L336)). Orca's [remote-server docs](https://github.com/stablyai/orca/blob/7146038cd38b8a50766dd2d78e3a8fff4fd097ea/docs/site/content/docs/remote-servers.mdx#L215-L227) describe the desktop host as living while the desktop app runs and headless `serve` as living while its process/service runs. The same docs say packaged macOS `orca serve` currently uses the desktop app server ([source](https://github.com/stablyai/orca/blob/7146038cd38b8a50766dd2d78e3a8fff4fd097ea/docs/site/content/docs/remote-servers.mdx#L169-L171)). **It is not a ready-made example of one always-on macOS ACP host with two thin local clients.**
- A separate **terminal/PTY daemon** owns subprocesses and terminal buffers; `orcad` disconnects from it without killing PTYs during a restart ([supervision](https://github.com/stablyai/orca/blob/7146038cd38b8a50766dd2d78e3a8fff4fd097ea/src/main/orcad/orcad-daemon-supervision.ts#L1-L58)). `orcad` nonetheless explicitly stops structured agent sessions on its own shutdown ([lifecycle](https://github.com/stablyai/orca/blob/7146038cd38b8a50766dd2d78e3a8fff4fd097ea/src/main/orcad/orcad-lifecycle.ts#L97-L111), [registration](https://github.com/stablyai/orca/blob/7146038cd38b8a50766dd2d78e3a8fff4fd097ea/src/main/orcad/orcad-entry.ts#L108-L128)). Terminal survival and live structured-session survival are different promises.

## How they avoid duplicate owners

- `orcad` acquires a **per-data-root instance lock before it creates the runtime**, then holds profile admission until runtime writers finish; lock publication is exclusive and stale-lock reclaim checks process identity rather than blindly deleting a path ([instance lock](https://github.com/stablyai/orca/blob/7146038cd38b8a50766dd2d78e3a8fff4fd097ea/src/main/orcad/orcad-instance-lock.ts#L119-L191), [runtime lifecycle](https://github.com/stablyai/orca/blob/7146038cd38b8a50766dd2d78e3a8fff4fd097ea/src/main/orcad/orcad-lifecycle.ts#L126-L163)). The terminal daemon separately issues a token and endpoint identity to authenticated clients, and checks endpoint ownership ([daemon server](https://github.com/stablyai/orca/blob/7146038cd38b8a50766dd2d78e3a8fff4fd097ea/src/main/daemon/daemon-server.ts#L110-L175), [endpoint lifecycle](https://github.com/stablyai/orca/blob/7146038cd38b8a50766dd2d78e3a8fff4fd097ea/src/main/daemon/daemon-endpoint-lifecycle.ts#L1-L104)). Its hello handshake includes protocol version, token, role, client ID, and process incarnation identity ([hello](https://github.com/stablyai/orca/blob/7146038cd38b8a50766dd2d78e3a8fff4fd097ea/src/main/daemon/daemon-client-hello-handshake.ts#L1-L112)).
- For macOS terminal-daemon survival across app updates, Orca can copy a signed helper outside the replaceable app bundle and launch it via a per-user `launchd` job, checking readiness and identity before adopting it ([stable bundle](https://github.com/stablyai/orca/blob/7146038cd38b8a50766dd2d78e3a8fff4fd097ea/src/main/daemon/macos-daemon-bundle.ts#L18-L45), [launchd](https://github.com/stablyai/orca/blob/7146038cd38b8a50766dd2d78e3a8fff4fd097ea/src/main/daemon/macos-daemon-launchd.ts#L44-L77), [adoption](https://github.com/stablyai/orca/blob/7146038cd38b8a50766dd2d78e3a8fff4fd097ea/src/main/daemon/macos-daemon-launchd.ts#L176-L234)). That path is conditional; the `orcad` path disables the macOS login-session launch option ([supervision](https://github.com/stablyai/orca/blob/7146038cd38b8a50766dd2d78e3a8fff4fd097ea/src/main/orcad/orcad-daemon-supervision.ts#L20-L33)).

## Clients and remote access

- A remote Orca host owns the repositories, Agent processes, credentials, and session state; paired clients reconnect to the existing host instead of starting a new one ([remote-server docs](https://github.com/stablyai/orca/blob/7146038cd38b8a50766dd2d78e3a8fff4fd097ea/docs/site/content/docs/remote-servers.mdx#L99-L115)). It uses revocable per-client pairing grants, recommends a private path such as Tailscale, and treats a pairing URL as a secret ([docs](https://github.com/stablyai/orca/blob/7146038cd38b8a50766dd2d78e3a8fff4fd097ea/docs/site/content/docs/remote-servers.mdx#L47-L85), [revocation](https://github.com/stablyai/orca/blob/7146038cd38b8a50766dd2d78e3a8fff4fd097ea/docs/site/content/docs/remote-servers.mdx#L113-L121)). `orcad` defaults to loopback and requires an explicit bind change for network exposure ([bind policy](https://github.com/stablyai/orca/blob/7146038cd38b8a50766dd2d78e3a8fff4fd097ea/src/main/orcad/orcad-bind-address.ts#L1-L46)).
- The headless Host can exit _when idle_, but only after checking clients, terminals, loaded chat providers, and other ongoing work; failed/unknown probes count as busy ([idle monitor](https://github.com/stablyai/orca/blob/7146038cd38b8a50766dd2d78e3a8fff4fd097ea/src/main/orcad/orcad-idle-exit-monitor.ts#L1-L91), [host probes](https://github.com/stablyai/orca/blob/7146038cd38b8a50766dd2d78e3a8fff4fd097ea/src/main/orcad/orcad-managed-idle-exit-host.ts#L65-L113)).

## Implications for Mischief

Keep the **one Host owns ACP, clients only send intents** direction from ADR 0003. The next meaningful implementation step is **exclusive profile ownership and safe restart/adoption**, not merely another readable socket: our current standalone `--daemon` socket is read-only, lacks authenticated client identity and stale-socket recovery, is not launched independently by either client, and does not own ACP. Orca's separate PTY daemon, signed-helper relocation, identity fencing and remote pairing solve requirements Orca already has; copy the constraints relevant to Mischief (safe ownership, update survival, client compatibility), not the whole machinery. In particular, moving ACP alone into a process that exits on app Quit would fail our agreed running-turn requirement.
